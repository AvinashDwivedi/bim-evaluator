# Evaluation Gold Standard

Use this contract when adding or reviewing evaluation cases. It is intentionally independent of any project, question wording, discipline, language, model, or target score.

## Reference requirements

- A reference must directly answer every requested dimension, metric, grouping, and relationship.
- Separate project observations, derived calculations, engineering interpretations, and external requirements.
- Record the population boundary, identity basis, source basis, units, null policy, and material exclusions needed to reproduce the answer.
- For ambiguous wording, define accepted interpretations or require the evaluated system to ask for clarification. Do not grade one unstated interpretation as uniquely correct.
- Do not use a project-wide inventory as the reference for a spatially restricted question unless evidence establishes that the populations are identical.
- A compliance reference must include both the applicable requirement and the project measurement needed for comparison. Inventory or metadata completeness alone is not a compliance result.
- A derived-metric reference must include the numerator, denominator, conversion assumptions, and result. Supporting-data counts alone do not answer the derived metric.

## Review and grading

- Require a source-backed human review before a case becomes release-blocking.
- Permit semantically equivalent answers with appropriate uncertainty; reject wrong scope, units, measurement basis, or unsupported certainty.
- Keep answer correctness separate from execution status, citation quality, source reconciliation, budget status, and latency.
- Use a judge independent from the answerer model family when practical, and periodically calibrate it against human decisions.
- Version references when project exports or standards change. Do not compare an answer from one snapshot with a reference derived from another.
